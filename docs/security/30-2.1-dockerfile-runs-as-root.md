# 30 — Scaffold Dockerfile runs as root

**CVSS:** 2.1 (Low) — `CVSS:3.1/AV:L/AC:H/PR:L/UI:N/S:U/C:L/I:L/A:L`

**Where:**
- `internal/cli/generator/templates/new/cmd/site/Dockerfile.tmpl:11-24` — final stage is `FROM alpine:3.21`, copies the binary in, no `RUN adduser`, no `USER` directive. `ENTRYPOINT` runs as root.

## What's wrong

The scaffolded container runs the app as UID 0. There's no operational reason for this — the binary doesn't bind to a privileged port (it listens on 8080), doesn't need to write to `/etc`, doesn't open raw sockets.

This is post-compromise hardening: if anything else in the audit becomes a remote-code-execution primitive (or the dev introduces one later), running as root amplifies the impact — easier filesystem access, easier escape attempts against the container runtime, easier abuse of writable mounts.

## Exploit

Not directly exploitable. Score reflects hardening debt that converts a hypothetical app-layer RCE from "limited blast radius" to "container-root, with whatever permissions the container has on host mounts."

## Fix

In the runtime stage of the Dockerfile:

```dockerfile
FROM alpine:3.21
RUN apk --no-cache add ca-certificates && \
    addgroup -S app && adduser -S -G app app
COPY --from=builder --chown=app:app /site /site
COPY --from=builder --chown=app:app /app/static /static

# For SQLite branch — ensure /data is owned by the app user
RUN mkdir -p /data && chown app:app /data
USER app

EXPOSE 8080
ENTRYPOINT ["/site"]
```

The `chown` flags on the COPY lines avoid the otherwise-common need for `chmod`/`chown` at runtime.
