# 04 — Media uploads buffered fully into memory

**CVSS:** 7.5 (High) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`

**Where:**
- `pkg/media/process.go:103` — `detectMIME` reads the entire upload into memory via `io.ReadAll`
- `pkg/media/video.go:16` — `probeVideoDuration` takes `data []byte` and pipes via `bytes.NewReader`
- `pkg/media/video.go:92` — `transcodeVideoToMP4` takes `data []byte`, writes to a temp file, then `os.ReadFile`s the output back into memory
- `pkg/media/image_store.go:197` — image pipeline runs `detectMIME` then `processImage` on the full byte slice

## What's wrong

Every image and video upload path holds the entire payload in process memory at least once (often twice — input bytes + decoded output bytes), regardless of `MaxSize`. There's no streaming, no spool-to-disk, no concurrency cap on in-flight uploads.

## Exploit

With the framework default `MaxSize` (e.g. 50MB for video), a few dozen concurrent uploads hold a few GB of heap. With S3 input, the transcode path also keeps the re-encoded output bytes in memory after the temp file read. Coordinated upload traffic exhausts memory and OOMs the process.

This is independent of the ffmpeg-decode-complexity angle (decompression bombs etc.) — it bites even on benign payloads at the documented max size.

## Fix

- Spool to a temp file as soon as `MaxSize` is established; pipe the temp file into ffmpeg/ffprobe.
- Return the transcoded bytes by reading the temp file as an `io.ReadCloser`, not `os.ReadFile`.
- Document the per-upload memory ceiling and a recommended concurrency limit; consider providing a semaphore wrapper.
