# 02 — Rate limiter trusts X-Forwarded-For; memory store grows unbounded

**CVSS:** 7.5 (High) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`

**Where:**
- `pkg/middleware/ratelimit.go:56-59` — default `KeyFunc` is `c.RealIP()`
- `pkg/middleware/ratelimit.go:150-162` — `NewMemoryStore` has no default size cap; `maxSize` is `0` (= unbounded) unless caller passes `WithMaxSize`
- Echo's `c.RealIP()` (`labstack/echo/v4` context.go:296) trusts `X-Forwarded-For` and `X-Real-IP` when `Echo.IPExtractor` is unset, which the scaffold doesn't set.

## What's wrong

Two compounding defaults:
1. The rate-limit key is the value Echo derives from `X-Forwarded-For` if present — controlled by the client unless a proxy strips it.
2. The in-memory store grows without bound by default.

## Exploit

An attacker sprays requests, varying `X-Forwarded-For` per request:
- Each unique header value becomes a new key → bypasses per-IP rate limiting wherever applied (e.g. login, password reset).
- Each unique key allocates a `window` struct in the map → memory grows linearly with attacker request count. No eviction unless `WithMaxSize` is set.

## Fix

- Require `IPExtractor` configuration on the server, or document trusted-proxy setup loudly. Default `KeyFunc` should fall back to `RemoteAddr` only if a trusted-proxy setup hasn't been declared.
- `NewMemoryStore` should default `maxSize` to a sane bound (e.g. 100k) and require an opt-out, not an opt-in.
