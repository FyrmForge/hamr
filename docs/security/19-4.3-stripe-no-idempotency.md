# 19 — Stripe webhook handler lacks idempotency

**CVSS:** 4.3 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N`

**Where:**
- `internal/cli/generator/templates/new/internal/api/handler/stripe/handler.go.tmpl:84-93` — `fn, ok := h.handlers[string(event.Type)]; if !ok { ... return 200 } if err := fn(ctx, event); err != nil { return 500 }`

Distinct from finding 01 (empty webhook secret). Assumes the secret is set and signature verification passes.

## What's wrong

After signature verification, the handler dispatches on `event.Type` and runs the registered callback. There's no check on `event.ID` for replay/dedupe. Stripe explicitly delivers events at-least-once: any 5xx response triggers retries, and even some 2xx paths can produce duplicates (slow network, late ACK).

The current code returns `500` on handler error, which guarantees Stripe will retry. Most handler stubs are no-ops, but the dev's real implementation will do things like "create order on `checkout.session.completed`."

## Exploit

Not really an external attack — more a self-inflicted problem at scale. But: an attacker who can cause a handler to fail partway (e.g. by forcing a downstream service the handler calls to error) reliably gets the same event re-delivered. Combined with non-idempotent state changes, this is "trigger the same accounting effect N times."

## Fix

Maintain a `processed_stripe_events` table keyed on `event.ID`. At handler dispatch:
1. `INSERT ... ON CONFLICT DO NOTHING RETURNING id`.
2. If no row inserted, return 200 immediately (already processed).
3. Otherwise run the handler; on success commit; on failure roll back the insert and return 5xx.

The scaffold should provide this glue, not just stub handlers.
