# 06 — Session tokens stored plaintext in DB

**CVSS:** 6.1 (Medium) — `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N`

**Where:**
- `pkg/auth/session.go:117-137` — `CreateSession` stores `Token` as-is
- `pkg/auth/session.go:141-165` — `ValidateSession` looks up by raw token
- `internal/cli/generator/templates/new/internal/db/migrations/001_initial.up.sql.tmpl:3-13` — `token TEXT NOT NULL UNIQUE`, indexed
- `internal/cli/generator/templates/new/internal/db/migrations/sqlite/001_initial.up.sql.tmpl:2` — same shape
- `internal/cli/generator/templates/new/internal/repo/postgres/store.go.tmpl:54` — `WHERE token = $1`
- `internal/cli/generator/templates/new/internal/repo/sqlite/store.go.tmpl:54` — same

## What's wrong

The session bearer token is stored verbatim in the database. The DB column **is** the live credential. There's no defense-in-depth between a DB compromise and full session hijack.

## Exploit

Anything that yields SQL read access — backup leak, hot-standby exposure, an analytics replica with looser ACLs, a SQLi in unrelated code, a curious operator with read access for support — produces a list of live session cookies. Attacker sets `Cookie: session_token=<row>` and is logged in as that user, no cracking, no MFA prompt, no further interaction.

Note also that `c.Cookie(...).Value` is logged or printed in routine debugging more often than one would like — same exposure, smaller surface.

## Fix

Standard pattern:
1. Mint random token `T` at session creation.
2. Send `T` to the client in the cookie.
3. Store `sha256(T)` (or HMAC under a server secret) in the `token` column; index on the hash.
4. On lookup, hash the incoming cookie and compare.

This is a contract change for `SessionStore`. The migration is one-shot: invalidate all existing sessions or run a backfill that re-hashes on next validation.
