# 21 — RenameModule follows symlinks during write-back

**CVSS:** 4.0 (Medium) — `CVSS:3.1/AV:L/AC:H/PR:L/UI:R/S:U/C:N/I:H/A:N`

**Where:**
- `internal/cli/generator/rename.go:31` (and walk loop) — walks the project tree, rewrites `.go` and `.templ` files via `os.WriteFile(path, ...)`. No symlink filter.

## What's wrong

`hamr rename` walks the project and rewrites import paths. `os.WriteFile` follows symlinks — if any `.go` or `.templ` file inside the project is actually a symlink to a file outside the project, the rename command overwrites the target.

## Exploit

CLI footgun, not a remote attack. Path requires:
- A malicious project (cloned from a hostile repo, etc.).
- The dev running `hamr rename` against it.

The attacker plants `evil.go → ~/.ssh/authorized_keys`. The rename rewriter sees a `.go` file, rewrites its bytes (likely garbling the imports), and writes it back through the symlink — corrupting or overwriting the target.

Combined with controlled content (carefully chosen module name → produces a chosen prefix line), this could be turned into an authorized_keys insertion. But that's high effort.

## Fix

During the walk, skip symlinks: `if d.Type()&fs.ModeSymlink != 0 { return nil }`. Optionally `Lstat` and refuse to write through any intermediate symlink in the path.
