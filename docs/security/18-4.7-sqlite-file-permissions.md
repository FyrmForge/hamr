# 18 — SQLite dir 0755; no enforced 0600 on .db/WAL

**CVSS:** 4.7 (Medium) — `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`

**Where:**
- `pkg/db/sqlite/sqlite.go:95` — `os.MkdirAll(dir, 0o755)` for the SQLite parent directory
- No explicit `os.Chmod` on the `.db` file or its `-wal` / `-shm` sidecars after open

## What's wrong

The SQLite-backed scaffold targets local-first / single-instance deploys, but doesn't enforce restrictive permissions. The DB file inherits whatever the umask and SQLite driver produce — typically `0644`. The WAL and SHM sidecars (which contain pages of recent writes) inherit similarly.

On a multi-tenant host or shared CI runner, every other user on the box can read the database.

## Exploit

Threat model: another local account on the same host. Bytes leak via direct read of `data/<project>.db`, `*.db-wal`, `*.db-shm`. Includes user data, password hashes, session tokens (see finding 06).

Not exploitable from the network. Realistic on shared dev machines, certain self-hosted PaaS, and CI environments.

## Fix

- `os.MkdirAll(dir, 0o700)` for the parent.
- After opening the DB, `os.Chmod` the `.db` file to `0600`. Same for the WAL/SHM as they appear (they're created lazily).
- Document the assumption ("HAMR's SQLite mode targets single-tenant hosts; multi-tenant deployments need stricter filesystem isolation").
