# 24 — CSRF wrapper leaves SameSite/Path on Echo defaults

**CVSS:** 3.5 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N`

**Where:**
- `pkg/middleware/csrf.go:8-34` — `CSRFConfig` exposes only `CookieName`, `TokenLookup`, `Secure`. SameSite, Path, MaxAge, HttpOnly are not exposed.

Echo's defaults (verified in pass B): `CookieMaxAge: 86400`, `CookieSameSite: SameSiteDefaultMode`, `CookiePath: ""`. So a HAMR project gets the Echo defaults for everything HAMR didn't expose.

## What's wrong

`SameSiteDefaultMode` is the empty `SameSite` attribute, which browsers interpret with their own defaults. Chrome's default is now `Lax`, but Firefox and Safari still differ in places. `CookiePath: ""` resolves to whatever the request path was when the cookie was set — usually `/`, but not guaranteed.

The CSRF mechanism itself (double-submit) is fine. The cookie hygiene around it is below what the rest of the framework asks for (e.g. session cookies set `SameSite: Lax` explicitly).

## Exploit

The classic CSRF threat — cross-site form post — is already blocked by the token check. The narrow residual risk is:
- A subdomain that shouldn't share the cookie ends up doing so because Path/Domain aren't pinned.
- A browser whose `SameSite` default isn't `Lax` gets weaker isolation than the framework's session cookie has.

## Fix

Expose `SameSite`, `Path`, `HttpOnly`, `MaxAge` on the HAMR `CSRFConfig`. Default to `SameSite: Lax`, `Path: /`, explicit `MaxAge`.

`HttpOnly` is a special case: the double-submit pattern relies on JavaScript reading the cookie to put it in a header. The scaffold actually reads the token from the hidden form field, not the cookie — so HttpOnly *could* be true, but verify all client paths before flipping.
