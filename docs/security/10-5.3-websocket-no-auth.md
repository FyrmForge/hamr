# 10 — `/ws` mounted with no auth

**CVSS:** 5.3 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`

**Where:**
- `internal/cli/generator/templates/new/internal/web/server.go.tmpl:76` — `e.GET("/ws", deps.Hub.Handler())` — no auth middleware
- `internal/cli/generator/templates/new/cmd/site/main.go.tmpl:256` — `hub := websocket.NewHub(websocket.WithLogger(log))` — no `WithSubjectIDFunc`
- `pkg/websocket/hub.go:97-132` — `Handler()` calls `ws.Accept` then registers the client; auth is captured at connect time and never re-checked

## What's wrong

The scaffolded `/ws` endpoint accepts anonymous WebSocket upgrades. The hub is constructed without `WithSubjectIDFunc`, so `Hub.Broadcast` and `Hub.SendToRoom` fan out to all connected clients regardless of who they are. There's no `RequireAuth()` on the route.

Independently, even when a subject identifier is configured, it's captured once at `Accept` time. Logout doesn't tear down the socket — the connection stays subscribed to `SendToSubject` until the client disconnects.

## Exploit

- Anonymous client connects to `wss://app/ws`.
- App code does `hub.Broadcast([]byte(notification))` for any "tell everyone" UX.
- Anonymous client receives it. If the notification body has any user-specific content (which it shouldn't, but devs will), it leaks.
- For the post-logout angle: user logs out, attacker (who got the cookie earlier) can keep the WS open and continue receiving `SendToSubject(victim)` traffic past logout.

## Fix

- Default `Hub.Handler()` to refuse upgrades without an authenticated subject; expose a `WithAllowAnonymous(true)` opt-in.
- Re-validate subject on every fan-out (cheap given the in-memory hub).
- Drop connections whose underlying session has been invalidated; expose a `Hub.RevokeSubject(id)` so the logout handler can call it.
