# 03 — Scaffold `.env` ships insecure defaults

**CVSS:** 7.5 (High) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N`

**Where:**
- `internal/cli/generator/templates/new/root/env.example.tmpl:12` — `postgres://...?sslmode=disable`
- `internal/cli/generator/templates/new/root/env.example.tmpl:22-26` — `S3_ACCESS_KEY=rustfsadmin`, `S3_SECRET_KEY=rustfsadmin`
- `internal/cli/generator/templates/new/root/env.example.tmpl:35-36` — `PGADMIN_EMAIL=admin@admin.com`, `PGADMIN_PASSWORD=admin`
- `internal/cli/generator/templates/new/root/env.example.tmpl:46-47` — `STRIPE_KEY=sk_test_dev_local`, `STRIPE_MOCK=true`
- `internal/cli/generator/project.go:262-263` — same template is rendered **twice**: once to `.env.example` and once to `.env`. So a freshly scaffolded project boots with these values.

## What's wrong

`hamr new` produces a `.env` (not just `.env.example`) prefilled with values that look production-shaped but are unsafe defaults. Three concrete problems:
- Postgres DSN with `sslmode=disable` — plaintext credentials and queries on the wire.
- Identical S3 access/secret keys (`rustfsadmin/rustfsadmin`).
- pgAdmin `admin/admin`.

Devs routinely treat `.env` as "already configured" and only edit specific values. The rest survives to production.

## Exploit

- DB connection over plaintext: passive sniff on the deploy network captures credentials and traffic.
- Default S3 keys: scan internet-exposed S3 endpoints — credentials are public.
- pgAdmin admin/admin: full DB access.

## Fix

- Don't render `.env` at scaffold time, only `.env.example`. Force the dev to create `.env` themselves.
- Replace credential-looking placeholders with obvious "REPLACE_ME" / random-generated sentinels.
- Default Postgres DSN to `sslmode=require` and document the local dev escape hatch separately.
