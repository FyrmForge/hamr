# 20 — CacheControl can mark dynamic auth content as `public`

**CVSS:** 4.3 (Medium) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/middleware/cache.go:67-87` — middleware sets `Cache-Control: public, max-age=N` based on URL suffix only (`.css`, `.js`, `.png`, …) or fingerprinted prefix
- `pkg/server/server.go:100` — middleware is registered globally with `CacheControl(false)` (i.e. disableCaching=false, not "this is a static path")

The matching condition is "URL ends in a known static extension." It runs *before* the handler. No knowledge of whether the response is per-user.

## What's wrong

Two failure modes:
1. A dynamic handler at a URL ending in `.css` or `.js` (think dev who exposes `/users/{id}/profile.js` for some HTMX-y reason) gets `public, max-age=86400` slapped on it.
2. More subtly, HTML pages get no `Cache-Control` at all from this middleware — meaning shared caches/CDNs apply their own heuristics, which can include caching authenticated content.

## Exploit

User A loads `/users/alice/profile.js` (dynamic, per-user). CDN sees `public, max-age=86400` and stores it. User B requests the same URL → gets Alice's data.

Realistic only when:
- A dev actually writes a dynamic endpoint with one of these suffixes (uncommon).
- The deploy has a shared cache (CDN, corporate proxy, intermediary) in front (common).

The HTML side is more common: any logged-in page with no explicit `Cache-Control` is at the mercy of intermediary caches' heuristics. Most modern CDNs won't cache `Set-Cookie`-bearing responses, but not all.

## Fix

- Default dynamic responses to `Cache-Control: private, no-store`. Static handlers opt into public caching, not the other way around.
- Restrict the suffix-match path to routes registered as static (Echo's `e.Static`/`e.StaticFS`), not the URL shape.
