# 07 — Media DetectType falls back to client Content-Type

**CVSS:** 6.1 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N`

**Where:**
- `pkg/media/media.go:332-369` — `DetectType` sniffs the first 512 bytes via `http.DetectContentType`, and if that doesn't classify into `imageTypes`/`videoTypes`, **falls back to the client-supplied `fh.Header.Get("Content-Type")`**.

## What's wrong

The fallback trusts a value the uploader controls. A file whose first 512 bytes don't match Go's stdlib sniffer can still be classified as `image/jpeg` (etc.) if the multipart header says so.

## Exploit

Craft an upload whose first 512 bytes are ambiguous to `http.DetectContentType` (or recognized as `application/octet-stream`), set `Content-Type: image/svg+xml` in the multipart part, and pass HAMR's "this is an image" check. The resulting file is whatever you uploaded but the app treats it as a benign image. Combined with finding [28](28-2.6-image-content-type-from-ext.md) (Content-Type derived from extension on serve), this becomes stored-XSS via uploaded SVG or HTML.

## Fix

Drop the header fallback entirely. If the magic-byte sniff doesn't classify, the upload is rejected. `http.DetectContentType` is intentionally lossy — that's the right answer.
