# 23 — Argon2 PHC version field not enforced

**CVSS:** 3.7 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/auth/auth.go:82-90` — `decodePHC` parses `v=%d` into a local `version` variable, then **never uses it**. The function returns `cfg, salt, hash, nil` regardless of what the version field said.

## What's wrong

PHC-format Argon2 strings include a version tag (`$argon2id$v=19$...`). HAMR parses but ignores it. A hash created under a different Argon2 version (e.g. `v=16`) will be re-verified using the current `golang.org/x/crypto/argon2` implementation against the current version, with no warning.

The Go `argon2` package itself documents that it implements version 1.3 (`v=19`). Pre-1.3 has known differences in how the H0 hash is constructed. A `v=16` hash compared against a `v=19` implementation will simply mismatch — meaning the practical failure is "legitimate passwords stop verifying after a library bump," not "wrong passwords verify."

So this is **not** an authentication-bypass primitive. It's a forward-compatibility / silent-failure trap.

## Exploit

No direct exploit. The score reflects "discoverable footgun that erodes the integrity of the hash store over time." If a future Argon2 standardizes `v=20` (or a different binding profile lands), HAMR will accept those PHC strings but verify them with the wrong algorithm — leading to mass auth lockout, or, in a worst case if the implementations diverge in a specific way, an `argon2.IDKey` collision.

## Fix

In `decodePHC`, compare the parsed version against `argon2.Version` and return an error on mismatch. One-line fix.
