# 05 — LocalStorage symlink traversal

**CVSS:** 6.6 (Medium) — `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N`

**Where:**
- `pkg/storage/local.go:55-65` — `resolve()` does lexical checks only (`filepath.Clean`, `IsAbs`, `..` prefix, basepath prefix)
- `pkg/storage/local.go:67-102` — `Save`/`Open`/`Delete`/`Exists` operate on the joined path with no symlink containment check

## What's wrong

`resolve()` is purely lexical. If any component inside `basePath` is a symlink that points outside the storage root, all four ops follow it. `Save` is particularly bad because `os.CreateTemp(dir, ...)` lands the temp file in the symlink target directory.

## Exploit

Pre-conditions: attacker can place a symlink under `basePath`. The realistic path is via another bug — a previous file upload that named a path which already existed as a symlink, or an admin tool that extracts user-controlled archives into the storage root.

With a symlink in place:
- Read: `Open("malicious-link/foo")` returns content from outside `basePath`.
- Write: `Save("malicious-link/foo", ...)` writes outside `basePath`, potentially overwriting host files the app has permission to.
- Delete: similarly escapes.

## Fix

Resolve each path component with `filepath.EvalSymlinks` after the lexical check and re-verify containment, or use `os.OpenInRoot` (Go 1.24+) / `openat2(RESOLVE_BENEATH)` semantics. The Save path additionally needs to refuse to write through any intermediate symlink in the target directory.
