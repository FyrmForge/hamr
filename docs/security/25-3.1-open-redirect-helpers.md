# 25 — Open-redirect-capable redirect helpers

**CVSS:** 3.1 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N`

**Where:**
- `pkg/respond/respond.go:30-36` — `Redirect(c, url)` passes `url` to `htmx.Redirect` or `c.Redirect(303, url)` with no validation
- `pkg/htmx/htmx.go:56-58` — `Redirect(w, url)` sets `HX-Redirect: <url>` directly
- `pkg/middleware/auth.go:167-173` — `redirect(c, url)` does the same dual-mode dispatch

## What's wrong

None of the redirect helpers validate the URL. Whatever the caller passes is what the browser is told to navigate to — relative or absolute, same-origin or not.

The framework doesn't expose a "safe redirect" alternative either. The first time a dev wires `respond.Redirect(c, c.QueryParam("next"))` (the canonical post-login pattern), it's an open redirect.

## Exploit

Phishing primitive:
- Attacker sends `https://app.example.com/login?next=https://evil.example.com/fake-app`.
- Victim logs in successfully. App redirects to `evil.example.com`. Victim sees the same UI they expect, types something sensitive on what they think is the dashboard.

Doesn't disclose data directly — but it converts a legitimate origin into a phishing launchpad.

## Fix

Provide a `respond.SafeRedirect(c, url)` (and equivalent in `pkg/htmx`) that:
- Parses the URL.
- Allows it through only if it has no scheme/host, or its host matches `BASE_URL`'s host.
- Falls back to a default safe URL otherwise (or returns an error).

Existing `Redirect` can stay for cases where the caller has already validated; ideally rename it to make the danger explicit, or deprecate.
