# 28 — Image serve sets Content-Type from extension

**CVSS:** 2.6 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/media/image_store.go:352-369` — `serveLocal` derives `Content-Type` from `filepath.Ext(storagePath)` via a small switch (`.webp`, `.jpeg`, `.jpg`, `.png`); anything unknown becomes `application/octet-stream`
- `pkg/media/image_store.go:390-407` — `serveS3` has the same logic

## What's wrong

The served Content-Type is decided from the filename extension, not from sniffing the stored bytes. If the stored content doesn't match the extension (because of finding 07: `DetectType` accepted a misclassified upload, or because an attacker overwrote the stored file via finding 05), the served response misrepresents the bytes.

Mitigated in practice by HAMR's global `Secure()` middleware setting `X-Content-Type-Options: nosniff`. With nosniff, the browser won't try to upgrade `application/octet-stream` to `text/html`, so a stored HTML payload served as octet-stream is treated as a download, not rendered.

But: nosniff is opt-in via the middleware. Devs who bypass `Secure()` (or apply it only to some routes) lose this defense.

## Exploit

Requires chaining with finding 07. Upload a polyglot whose magic bytes confuse `http.DetectContentType` and whose `Content-Type` header claims `image/jpeg`. The store accepts it as an image. The serve handler returns it with `Content-Type: image/jpeg`. If `nosniff` is in place, no problem. Without `nosniff`, a browser that decides to render it as HTML executes whatever HTML/JS is inside.

## Fix

Either:
- Sniff the first 512 bytes of the stored file at serve time and use that for `Content-Type`. Slow but correct.
- Persist the validated MIME type alongside the file at upload time and serve from that.

Add `Content-Disposition: inline; filename="..."` so even if a misclassification slips through, the browser at least gets an explicit hint.
