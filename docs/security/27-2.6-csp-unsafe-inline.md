# 27 — CSP allows `'unsafe-inline'` on script-src/style-src

**CVSS:** 2.6 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N`

**Where:**
- `internal/cli/generator/templates/new/internal/web/server.go.tmpl:80` — `csp := "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'"`
- `internal/cli/generator/templates/new/internal/web/components/layout.templ.tmpl:58-71` — inline `<script>` block configures HTMX response handling and adds the CSRF header to HTMX requests

## What's wrong

The scaffolded CSP allows inline scripts and styles. This nukes CSP's main contribution to XSS defense-in-depth — any successful HTML injection becomes executable JS without needing to bypass CSP.

`'unsafe-inline'` is there because the layout template embeds two inline `<script>` blocks. The fix is to extract those scripts into static files, not to keep the CSP weak.

## Exploit

CSP doesn't create vulnerabilities — it limits the blast radius of one. So this finding is "if you also have an XSS somewhere, this CSP doesn't slow the attacker down." On its own it's not exploitable.

Because templ auto-escapes string output, the scaffolded surface has no obvious XSS sink. But the framework's job is to make hard-to-spot XSS bugs less catastrophic; this default does the opposite.

## Fix

- Move the inline `<script>` in `layout.templ.tmpl` to `static/js/htmx-init.js` (or similar) and load it via `<script src=...>`.
- Drop `'unsafe-inline'` from `script-src` and `style-src` in the CSP.
- For one-off inline blocks that must stay, use CSP nonces — render a per-request nonce into the page, add `script-src 'nonce-{nonce}'`.
