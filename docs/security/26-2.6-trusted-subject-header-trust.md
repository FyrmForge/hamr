# 26 — TrustedSubject blindly trusts X-Subject-ID

**CVSS:** 2.6 (Low) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:N`

**Footgun path:** If used on a publicly-routable endpoint, score is effectively `9.8 CRITICAL` (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N`) — full impersonation.

**Where:**
- `pkg/middleware/trusted.go:8-30` — reads `X-Subject-ID` from the request and writes it into `ctx.SubjectIDKey` with no verification

## What's wrong

The middleware copies an HTTP header into the same context slot that the real session-based auth uses. Downstream handlers can't distinguish a request authenticated by session-validation from one authenticated by `X-Subject-ID: <anything>`.

The package doc comment says "use only behind authenticated infrastructure boundaries." There's no enforcement: no IP allowlist, no shared-secret HMAC, no mTLS check. The function name (`TrustedSubject`) is the only guardrail.

## Exploit

Two scenarios:

1. **Correct use** (behind a gateway that strips client-supplied `X-Subject-ID` and adds its own): the score is low — attackers can't reach the middleware directly.
2. **Misuse** (any case where attacker-controlled `X-Subject-ID` reaches the handler): full account impersonation. Send `X-Subject-ID: <victim-uuid>` and every authenticated action runs as the victim.

The realistic misuse path is a developer who wants the middleware's drop-in compatibility with `GetSubjectID(c)` but doesn't have the gateway architecture the doc assumes. The route name is identical between the two paths.

## Fix

- Require the caller to provide either (a) a list of trusted source IPs, or (b) an HMAC verifier for the incoming `X-Subject-ID`. The middleware refuses to construct without one of those.
- Rename to something louder: `UntrustedSubjectFromHeader` or `BehindAuthenticatedProxy(allowedSources []net.IPNet)`.
- Add a runtime check that logs (loudly) on first request: "this middleware is configured without an IP allowlist; ensure your deployment strips client X-Subject-ID."
