# 16 — Global gzip → BREACH on authenticated HTML

**CVSS:** 4.8 (Medium) — `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/server/server.go:101-107` — `e.Use(echoMw.GzipWithConfig(...))` applied globally when `gzipConfig.Enabled` (default true)

## What's wrong

Compression is enabled on every response, including authenticated HTML that contains secrets (CSRF tokens, session-linked user identifiers, etc.) alongside any reflected user input. That's the classic BREACH precondition.

## Exploit

Attacker needs:
1. Victim visits an attacker-controlled page that triggers cross-origin requests to the HAMR app while authenticated.
2. The attacker can observe the encrypted response sizes (passive, on-path).
3. The HAMR page reflects a request parameter the attacker controls.

By guessing one character of the CSRF token at a time and observing whether the gzipped response shrinks (the guess shared a dictionary prefix with the real token), the attacker recovers the token byte by byte.

Realistic? Modern browsers' SameSite defaults and HTTP/2 padding semantics make this harder than the original 2013 BREACH, hence `AC:H`. But the framework still hands attackers a primitive it shouldn't.

## Fix

- Don't gzip responses that carry a session cookie *and* reflect any request parameter. A practical version: skip gzip on responses with `Content-Type: text/html` for authenticated users, or skip on any response with a `Vary: Cookie` header.
- Alternative: random per-response padding via `Vary: Accept-Encoding` plus a randomized header to break the length oracle. More involved.
