# 11 — No HTTP socket timeouts (slowloris-class DoS)

**CVSS:** 5.3 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L`

**Where:**
- `pkg/server/server.go:97-99` — only sets a context timeout middleware
- `pkg/server/server.go:193` — `s.echo.Start(addr)`
- `pkg/server/options.go` — no `WithReadTimeout` / `WithWriteTimeout` / `WithIdleTimeout` / `WithReadHeaderTimeout` option exposed

## What's wrong

Echo's `Start` constructs an `http.Server` with all four timeout fields at their zero values, meaning unlimited. The context-timeout middleware only fires once the request reaches handler execution — it does nothing about a client that takes minutes to send a header. HAMR provides no option to set these on the underlying server.

## Exploit

Classic slowloris: open N connections, send a partial header line every ~30s. Each connection holds a goroutine and a file descriptor indefinitely. Process eventually hits `ulimit -n` or `GOMAXPROCS`-bounded scheduler pressure.

A modern reverse proxy in front (nginx, Caddy) usually mitigates this — which is why the score is `A:L`, not `A:H`. But "deploy behind a reverse proxy" is an assumption HAMR doesn't document and doesn't enforce.

## Fix

- Expose `WithReadTimeout`, `WithReadHeaderTimeout`, `WithWriteTimeout`, `WithIdleTimeout` on the server options.
- Set safe defaults: e.g. `ReadHeaderTimeout: 10s`, `ReadTimeout: 30s`, `WriteTimeout: 30s`, `IdleTimeout: 120s`.
- Document the proxy-vs-direct deployment model.
