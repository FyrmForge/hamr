# 29 — Unsigned flash cookie

**CVSS:** 2.6 (Low) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/middleware/flash.go:46-56` — cookie carries `base64(json.Marshal(FlashMessage{Message, Type}))` with no signature
- `pkg/middleware/flash.go:73-89` — middleware decodes the cookie and trusts the contents

## What's wrong

The flash cookie is integrity-protected only by `HttpOnly + SameSite Lax + per-browser scope`. The value itself is base64-encoded JSON the browser stores. Anyone who can write the cookie (the user themselves, browser-extension code, or any same-origin JS) can forge arbitrary flash content.

Templ auto-escapes `flash.Message` when rendered, so this isn't an XSS sink directly. The real damage is:
- A user can show themselves "deletion successful" banners that never happened, then claim the system did something it didn't.
- If the dev ever uses `flash.Type` (string) in a class attribute or class-lookup table, attacker-chosen values can drop arbitrary classes.

## Exploit

Limited blast radius: each forgery only affects the forger's own browser. So this is essentially self-XSS-level. The CVSS reflects "low-impact integrity to messages the user sees about themselves," not "compromise of other users."

## Fix

HMAC the cookie payload with a server-side secret. Verify on read; drop the flash silently on mismatch. Standard signed-cookie pattern — keep the message as the cleartext part, append a tag.

Alternative: move flash state to the session row (one column) and reference it from the cookie by session ID only.
