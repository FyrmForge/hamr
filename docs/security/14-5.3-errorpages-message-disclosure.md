# 14 — ErrorPages reflects HTTPError.Message into 5xx page

**CVSS:** 5.3 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`

**Where:**
- `pkg/middleware/errors.go:46-68` — `if he, ok := err.(*echo.HTTPError); ok { ... message = m }`, then `respond.HTML(c, code, page(code, message))` — message is rendered even for `code >= 500`
- `internal/cli/generator/templates/new/internal/web/components/error.templ.tmpl:19,27` — `<p ...>{ message }</p>` in both Tailwind and plain branches

## What's wrong

`ErrorPages` middleware takes the `Message` field of an `echo.HTTPError` and renders it into the page for any status code, including 500+. The scaffold's `error.templ` displays it directly. Devs write `echo.NewHTTPError(http.StatusInternalServerError, err.Error())` all the time — they expect `err.Error()` to land in a log file, not the user's browser.

## Exploit

Find any handler path that wraps an error into `NewHTTPError(500, ...)`. The wrapped string ends up in the rendered HTML. Common payloads:
- Underlying SQL error: `pq: column "x" of relation "users" does not exist` → schema disclosure.
- Filesystem error: `/var/app/data/secrets.key: permission denied` → path disclosure.
- Upstream API response: HTTP body of a failed external call → can include tokens.

## Fix

In `ErrorPages`, for `code >= 500`, force `message = http.StatusText(code)` regardless of what the `HTTPError` carries. Continue logging the real error with `logging.Error`. The current implementation already does the log — it just also leaks the message.
