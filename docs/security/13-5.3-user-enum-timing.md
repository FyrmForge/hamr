# 13 — User-enumeration timing in Authenticate

**CVSS:** 5.3 (Medium) — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`

**Where:**
- `internal/cli/generator/templates/new/internal/service/auth.go.tmpl:65-83` — `Authenticate` returns `ErrInvalidCredentials` immediately if `user == nil`, then runs Argon2id only when the user exists

## What's wrong

Two response paths with very different cost profiles:
- Unknown user: one DB lookup, ~1ms.
- Known user, wrong password: DB lookup + Argon2id (default params: 64MiB / t=3 / p=2 → ~50–100ms on commodity hardware).

The latency difference is large, stable, and observable over any network without elaborate side-channel work.

The register flow leaks the same information differently — see finding 12 — but timing on `/login` is independent.

## Exploit

Submit `<email>:wrong-password` against `/login` for a list of candidate emails. Measure response time. Anything slower than ~30ms → email is registered. Output: validated list of accounts to credential-stuff or phish.

The downstream of an enumerated list is more dangerous than the leak itself — it converts a generic credential-stuffing operation into a targeted one.

## Fix

When the user lookup misses, run a `auth.CheckPassword` against a fixed dummy Argon2id hash to equalize the wall clock. The framework can ship the dummy hash as a package constant. Slightly wasteful in the cold path; acceptable tradeoff.
