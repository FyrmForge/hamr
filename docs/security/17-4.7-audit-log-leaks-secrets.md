# 17 — Audit middleware logs raw query strings + path params

**CVSS:** 4.7 (Medium) — `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`

**Where:**
- `pkg/middleware/audit.go:53-69` — entry includes `data["query"] = c.Request().URL.RawQuery` and `data["path_params"] = params` for every non-GET mutation
- `internal/cli/generator/templates/new/internal/web/handler/auth/login/handler.go.tmpl:68` and `register/handler.go.tmpl:70` separately log the user's email on failed attempts via `log.Warn(...)`

## What's wrong

Audit log entries land in whatever sink the app provides — DB table, log aggregator, file on disk. They include:
- Full `RawQuery` for any non-GET, which routinely carries one-shot tokens (password reset, email confirmation, magic-link, OAuth state).
- Full `path_params` for the same routes.
- Separately: login/register handlers log email addresses on every failure.

This is "PII / secret-bearing data flowing into operational logs by default."

## Exploit

Whoever can read the logs reads the secrets. Realistic profiles:
- Support engineer with read access to the audit table → discovers active password-reset tokens.
- SIEM operator → has full visibility into URLs containing API tokens.
- Backup leak → same.

The exposure scales linearly with how widely logs are shared.

## Fix

- Audit entries should record route pattern + method + status, never raw URLs/queries.
- For projects that want richer data, expose a per-route allowlist of params to record.
- Login/register handlers should log a stable user ID (after lookup succeeds) or an opaque hash of the email, not the email.
